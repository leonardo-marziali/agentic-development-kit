# CHANGELOG.md Generation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wire `@semantic-release/changelog` and `@semantic-release/git` into
this repo's semantic-release pipeline so a `CHANGELOG.md` is generated and
committed to `main` on every release, instead of release notes living only on
GitHub's Releases page.

**Architecture:** Config-only change. Add two plugins to `release.config.js`
in the standard semantic-release order (changelog write, then git commit,
both before the GitHub publish step), add the two packages as
devDependencies, and update the two doc spots that currently assert
`@semantic-release/git` is deliberately excluded. No workflow file changes
and no application code — this repo has no code paths touched by this
feature.

**Tech Stack:** semantic-release, pnpm, GitHub Actions (existing).

## Global Constraints

- Spec: `docs/superpowers/specs/2026-09-06-changelog-generation-design.md`
- Package manager is pnpm exclusively (per `AGENT.md`) — never `npm`/`yarn`.
- Commits must follow Conventional Commits (commitlint + husky `commit-msg`
  hook enforce this locally).

- Do not touch `.github/workflows/release.yml`, `commitlint.config.js`,

### Task 2: Wire the plugins into release.config.js

**Files:**

- Modify: `release.config.js`

**Interfaces:**

- Consumes: `@semantic-release/changelog`, `@semantic-release/git` from
  Task 1's `node_modules`.
- Produces: the plugin list and options that Task 3's docs describe — keep
  the two in sync (same plugin order, same `assets` value, same reliance on
  the plugin's default commit message).

- [ ] **Step 1: Replace the plugin list and header comment**

Replace the full contents of `release.config.js` with:

```js
// This repo is a private plugin marketplace, not an npm package — the
// version that matters is the git tag / GitHub release, not package.json's
// "version" field. There's no @semantic-release/npm (nothing to publish),
// so package.json's "version" field intentionally stays "0.0.0" and only
// CHANGELOG.md is committed back to main by @semantic-release/git — see
// README's "Releases & versioning" for why that push is safe here (it needs
// a branch-protection bypass actor for the release workflow, tracked
// separately in this repo's Terraform-managed rulesets).
module.exports = {
  branches: ['main'],
  plugins: [
    '@semantic-release/commit-analyzer',
    '@semantic-release/release-notes-generator',
    '@semantic-release/changelog',
    [
      '@semantic-release/git',
      {
        assets: ['CHANGELOG.md'],
      },
    ],
    '@semantic-release/github',
  ],
};
```

- [ ] **Step 2: Sanity-check the config loads**

Run: `node -e "console.log(require('./release.config.js'))"`
Expected: prints the object above with no throw — confirms valid JS syntax
and that requiring the two new plugin package names doesn't error (semantic
release itself resolves plugins lazily by string name via its own loader,
but a plain `node -e` require of the config file alone is enough to catch
JS syntax mistakes here since the config is plain data, not a
plugin-resolution call).

- [ ] **Step 3: Dry-run semantic-release locally to confirm plugin resolution**

Run: `pnpm exec semantic-release --dry-run --no-ci`
Expected: it will fail (no `GH_TOKEN`/`GITHUB_TOKEN` set locally, and this
isn't a CI branch context) — but the failure must be about missing
credentials/branch context, NOT about a missing or unresolvable plugin
module (e.g. NOT `Cannot find module '@semantic-release/changelog'`). If the
error is a plugin-resolution error, Task 1 didn't complete correctly — redo
it.

- [ ] **Step 4: Commit**

```bash
git add release.config.js
git commit -m "feat(release): generate and commit CHANGELOG.md on release"
```
